## [STAGE 01] Instruction encoding, register file, control unit

We built the three "front-end" parts of a core: the instruction decoder (`isa.py`), the register file (`registers.py`), and the control unit (`control.py`). Like MIPS in the lectures, each instruction is a binary word split into fixed fields, but ours is 16 bits: the top 4 bits are the opcode, the next 3 bits name Rd, then Rs and Rt — for example `ADD R1, R2, R3` encodes as `0000 001 010 011 000` = `0x0298`, and `STORE R3, [240]` as `1001 011 11110000 0` = `0x97E0` (this exact field layout is our documented design decision; the PDF gives only the 16-bit width and the instruction list). The decoder rejects bad words such as unknown opcode `1100` or a nonzero unused bit, just as real hardware would treat them as illegal instructions. Each `RegisterFile` object owns eight separate 8-bit registers (0..255, all writable including R0), so writing R7 in one core's file cannot change another core's R7 — this is the basis for independent cores later. The control unit reads the opcode and raises control signals: ALU instructions set `reg_write` and choose `alu_op`, `LOAD` sets `mem_read` + `reg_write`, `STORE` sets only `mem_write`, and `HALT` sets none. Execution and the program counter come in stage 02; the PC will be a list index that advances by 1, not MIPS PC+4 (implementation choice, see CLAUDE.md).
