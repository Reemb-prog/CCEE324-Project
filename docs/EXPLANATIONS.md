## [STAGE 01] Instruction encoding, register file, control unit

We built the three "front-end" parts of a core: the instruction decoder (`isa.py`), the register file (`registers.py`), and the control unit (`control.py`). Like MIPS in the lectures, each instruction is a binary word split into fixed fields, but ours is 16 bits: the top 4 bits are the opcode, the next 3 bits name Rd, then Rs and Rt — for example `ADD R1, R2, R3` encodes as `0000 001 010 011 000` = `0x0298`, and `STORE R3, [240]` as `1001 011 11110000 0` = `0x97E0` (this exact field layout is our documented design decision; the PDF gives only the 16-bit width and the instruction list). The decoder rejects bad words such as unknown opcode `1100` or a nonzero unused bit, just as real hardware would treat them as illegal instructions. Each `RegisterFile` object owns eight separate 8-bit registers (0..255, all writable including R0), so writing R7 in one core's file cannot change another core's R7 — this is the basis for independent cores later. The control unit reads the opcode and raises the same signals as the lecture's single-cycle MIPS control table — RegDst, ALUSrc, MemtoReg, RegWrite, MemRead, MemWrite, ALUOp — for example `ADD` gives `RegDst=1, ALUSrc=0, MemtoReg=0, RegWrite=1, ALUOp=ADD`, while `LOAD` gives `MemRead=1, MemtoReg=1, RegWrite=1` so the memory byte, not an ALU result, is written back; `STORE` sets only `MemWrite`, and `HALT` sets none. A few values differ from MIPS because our LOAD/STORE use an absolute address (no base+offset, so the ALU is idle and ALUSrc/ALUOp are "don't care") and there are no branches; the full comparison table is in `docs/ARCHITECTURE.md`. Execution and the program counter come in stage 02; the PC will be a list index that advances by 1, not MIPS PC+4 (implementation choice, see CLAUDE.md).

## [STAGE 02] ALU and a working single core

We built the ALU (`alu.py`), the 256-byte data memory class (`memory.py`), and a core (`core.py`) whose `step()` runs exactly one instruction through the same cycle as the lecture's single-cycle datapath: fetch the word at PC, decode it, read Rs and Rt, let the ALU compute, write the result into Rd, and move the PC on. Every result is masked to 8 bits, so `ADD 250 + 10` gives `4` (the carry out of bit 7 is lost), and subtraction is two's-complement addition: `3 - 5` is `3 + (~5 + 1) = 3 + 251 = 254`, which is the 8-bit bit pattern `11111110` for −2. The logical operations work bit by bit (`0xAA AND 0x0F = 0x0A`, `NOR` is `NOT(OR)`), and shifts move bits out of the 8-bit window, so `SLL 0x40 by 2` gives `0x00` and any shift of 8 or more gives 0. Worked trace: with R1=200 and R2=100, `ADD R3,R1,R2` stores 44 (300 − 256) and the PC goes 0→1, `SUB R4,R3,R1` stores 44 − 200 = 100 (mod 256) and the PC goes 1→2, and `HALT` sets `halted` and leaves the PC at 2 forever. The PC counts instructions in the list (+1 each step) rather than bytes (MIPS +4), which is our implementation choice because instructions live in a Python list, not byte-addressed memory; LOAD/STORE are wired in stage 04.

## [STAGE 03] Two independent cores sharing one clock

We built `processor.py`, which creates two completely separate `Core` objects — each with its own PC, its own eight registers, its own decoder/control unit and ALU, and its own instruction program — plus one shared data memory for later. "Two PCs" means two separate state variables (`cores[0].pc` and `cores[1].pc`), not two different numbers: after the first tick both hold 1, yet changing one never changes the other, exactly like two people both standing on step 1 of two different staircases. Each `tick()` is one conceptual clock cycle in which every non-halted core executes one instruction; the cores are stepped one after the other in ordinary Python (no threads), which models "same cycle" for a teaching simulator, not true parallel hardware. Worked example: core 0 runs `ADD R3,R1,R2; HALT` with R1=8, R2=4, and core 1 runs `XOR R3,R1,R2; ADD R4,R3,R1; HALT` with R1=10, R2=3 — after tick 1 core 0's R3 is 12 and core 1's R3 is 9 (same register name, different register files); at tick 2 core 0 halts with its PC frozen at 1 while core 1 keeps going to PC 2; at tick 3 core 1 halts with R4 = 9 + 10 = 19, so `cycles` = 3. If a program never halts, `run(max_cycles)` stops with an error instead of looping forever.
